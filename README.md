# AEM Orchestrator

AEM Orchestrator is a stateless Java application for orchestrating AEM infrastructure created using [aem-aws-stack-builder](https://github.com/shinesolutions/aem-aws-stack-builder). It's primary function is to keep Adobe Experience Manager (AEM) running in a healthy state despite scaling events or other such impacts on the stack. It does this by listening to a predefined SQS queue and reacting to changes on the stack.

## Installation

### Requirements

This project requires Java 21 and Apache Maven 3.10+. Run the `make` targets inside the
[aem-platform-buildenv](https://github.com/shinesolutions/aem-platform-buildenv) Docker image, as CI does.

### Download

Releases are published to [Maven Central](https://central.sonatype.com/namespace/com.shinesolutions)
under `com.shinesolutions:aem-orchestrator`.

### Build from source

| Target | Description |
|---|---|
| `make deps` | Download all dependencies and plugins |
| `make build` | Package the JAR without running tests |

```
$ make build
```
This will create a JAR file in the '\target' directory called aem-orchestrator-x.x.x.jar.
By default the generated JAR file will contain all of the required dependencies

## Usage

### Requirements
The AEM Orchestrator requires [aem-aws-stack-builder](https://github.com/shinesolutions/aem-aws-stack-builder) to have created a stack in order to work. You'll need to get this running before attempting to run AEM Orchestrator. If using puppet then you should also take a look at [puppet-aem-orchestrator](https://github.com/shinesolutions/puppet-aem-orchestrator).

The AEM Orchestrator uses [AWS Instance Profiles](http://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-ec2_instance-profiles.html) authentication. If you do not already have this, you will need to set it up.

### Configuration
The application requires there to be an application.properties file in the same base directory as the JAR file. Here is an example of a properties file with the minimum properties set:

```properties
aws.cloudformation.stackName.author = example-aem-author-stack
aws.cloudformation.stackName.authorDispatcher = example-aem-author-dispatcher-stack
aws.cloudformation.stackName.publish = example-aem-publish-stack
aws.cloudformation.stackName.publishDispatcher = example-aem-publish-dispatcher-stack
aws.cloudformation.stackName.messaging = example-aem-messaging-stack
aws.sqs.queueName = example-aem-asg-event-queue
```

The aem-aws-stack-builder will generate these names for you, they just need to be added to this Orchestrator application.properties file. See [here](docs/configuration.md) for more information on configuration properties. You can also view the base [application.properties](src/main/resources/application.properties) file.

### Running the JAR
Run the JAR with Java 21:

```
$ java -jar aem-orchestrator-x.x.x.jar
```

Since the upgrade to Spring Boot 4 the JAR is no longer a 'fully executable' jar, so it can't be run directly as `./aem-orchestrator-x.x.x.jar`.
To run it as a systemd service, use `ExecStart=/usr/bin/java -jar /path/to/aem-orchestrator.jar`, as [puppet-aem-orchestrator](https://github.com/shinesolutions/puppet-aem-orchestrator) does.

### Logging
By default the Orchestrator will log to a file called *orchestrator.log* in the root directory. It uses [logback](https://logback.qos.ch/) and here is the default [configuration file](src/main/resources/logback.xml). Note that debug is enabled by default. To override the default logging, place your custom logback.xml file in the same directory as the JAR file.

### Events
The AEM Orchestrator reacts to three different types of events:

1. [Instance Scale Up](docs/scale-up-events.md)
2. [Instance Scale Down](docs/scale-down-events.md)
3. [Alarms](docs/alarms.md)

#### Scale Events
The scale up and scale down events are generated by the AWS autoscaling groups (ASG). These can occur at the following tiers of the stack:

* Author Dispatcher
* Publish
* Publish Dispatcher

For example if a Publish instance stopped responding the ASG would terminate it, which would generate a message to the Orchestrator to perform a *Scale Down Publish Action*. The ASG would also start a new Publish instance, which would generate a *Scale Up Publish Action*. In each case, the AWS instance ID is passed to the Orchestrator so that it can perform it's action.

#### Alarms
Currently there is only one alarm, the [AEM Content Health Check](https://github.com/shinesolutions/aem-aws-stack-provisioner/blob/master/templates/aem-tools/content-healthcheck.py.epp). This will trigger if the Publish Dispatcher is not seeing healthy content (defined in a [descriptor file](https://github.com/shinesolutions/aem-aws-stack-provisioner/blob/master/examples/content-healthcheck-descriptor.json)) on the Publish instance. When the alarm triggers the Orchestrator is notified via an SQS message and it will perform an *Alarm Content Health Check Action*.

### Reading Messages
The AEM Orchestrator attaches itself as a listener to the SQS queue defined in the application.properties. It works in an asynchronous manner and does **not** poll the queue. Only one message is processed at a time (no concurrency). There is no guarantee to the order of processing, but the Orchestrator is designed to handle messages in any order.

The message format is the Amazon SNS [HTTP/HTTPS Notification JSON Format](http://docs.aws.amazon.com/sns/latest/dg/json-formats.html). A JSON definition of the format can be found [here](https://sns.us-west-2.amazonaws.com/doc/2010-03-31/Notification.json).

## Result Model

Each event is handled by an action (for example *Scale Up Publish Action*) for the AWS instance ID in the message. Every action implements [Action](src/main/java/com/shinesolutions/aemorchestrator/actions/Action.java) and returns a boolean result that decides what happens to the SQS message:

* `true`: the message is acknowledged and removed from the queue
* `false`: the message is left on the queue, so it is redelivered and retried later

Because the result is kept on the queue, in essence the queue holds the state of the stack, not the AEM Orchestrator.

Each result is logged. Here is a log example (with debug off) for a successful *Scale Up Publish Dispatcher Action*:

```
INFO  c.s.a.s.OrchestratorMessageListener - Message received ID:3dfea271-254c-4cef-a793-ff67a2218239
INFO  c.s.a.a.ScaleUpPublishDispatcherAction - ScaleUpPublishDispatcherAction executing
INFO  c.s.a.a.ScaleUpPublishDispatcherAction - Desired capacity already matching for publish auto scaling group and it's dispatcher. No changes will be made
INFO  c.s.a.s.OrchestratorMessageListener - Acknowledged message (removing from queue): ID:3dfea271-254c-4cef-a793-ff67a2218239
```

## Error Handling

If the Orchestrator fails to perform an action on a message for what ever reason, the message will not be acknowledged and instead kept in flight on the queue to be reprocessed at a later time. The log shows `Leaving message <ID> on the queue`.

### Recovery
Aside from stack startup, the AEM Orchestrator is designed to recover the stack from multiple scenarios:

* Termination of a single instance (Author Dispatcher, Publish or Publish Dispatcher)
* Termination of many or all instances
* Scale up of a single instance (Author Dispatcher, Publish or Publish Dispatcher)
* Scale up of all instances

**NOTE**: The AEM Orchestrator must be running to perform this recovery, however due to it's stateless nature, the AEM Orchestrator can be started post termination or scale up of an instance. Upon startup, it will begin processing messages off the SQS queue.

### Troubleshooting
If all goes well at start up you should see something like this in your log file:

```
DEBUG c.s.a.s.OrchestratorMessageListener - Initialising message receiver, starting SQS connection
INFO  c.s.aemorchestrator.AemOrchestrator - AEM Orchestrator started
```
Otherwise you will need to view the *orchestrator.log* and try and decipher what is going wrong. Most likely causes are:

* Stack not properly initialised
* Invalid or missing IAM role permissions
* Invalid or missing property in the application.properties file
* AEM not in a healthy state on author or publish instances
* AWS Instance Profile authentication not set up

Upon startup of the stack you will see the Orchestrator log showing the processing of many messages (see [Result Model](#result-model)). If the Orchestrator log isn't moving but there are definitely messages in the SQS queue, then something may be wrong (refer to likely causes above).

## Versions History

Changes in each version are described in [CHANGELOG.md](CHANGELOG.md).

Releases are published to [Maven Central](https://central.sonatype.com/namespace/com.shinesolutions)
under `com.shinesolutions:aem-orchestrator` and tagged `aem-orchestrator-<version>` in git.
Versions follow [Semantic Versioning](https://semver.org/): use a major release for breaking changes
(e.g. a new Java runtime or changed properties), minor for new features and patch for fixes.
Between releases, `pom.xml` holds the next pre-release version, e.g. `4.0.1-pre.0`.

Versions are managed with [RTK](https://github.com/cliffano/rtk), configured in `.rtk.json`: it sets
the release version in `pom.xml` and CHANGELOG.md, commits and tags it `aem-orchestrator-<version>`,
then commits the next pre-release version.

### Release targets

| Target | Description |
|---|---|
| `make release-check` | Offline release dry run: GPG-sign and bundle the committed `HEAD` for Maven Central at its release version, check the bundle and every signature, upload nothing. Signs with `MAVEN_GPG_KEY` (armored secret key) and `MAVEN_GPG_PASSPHRASE` from the environment, or your GPG keyring; bundle kept at `target/release-check/central-bundle.zip` |
| `make release-test RELEASE_TEST_VERSION=<x.y.z-rc.n>` | Run on your machine: in aem-platform-buildenv (Docker), sign `HEAD` and upload it to the Maven Central Portal as a pre-release test version without publishing it, then print the deployment ID for `release-status` and `release-drop`. Only pre-release versions are accepted (default: current release version with `-rc.0`) |
| `make release-status DEPLOYMENT_ID=<id>` | Show a Maven Central Portal deployment's state (e.g. `VALIDATED`, `PUBLISHED`, `FAILED`) and errors, using `MAVEN_CENTRAL_USERNAME` and `MAVEN_CENTRAL_PASSWORD` |
| `make release-drop DEPLOYMENT_ID=<id>` | Drop (delete) a Maven Central Portal deployment that has not been published |
| `make publish` | Sign the checked-out version and upload it to the Maven Central Portal, then wait until it is validated. Run by the **Publish to Maven Central** workflow on a pushed `aem-orchestrator-<version>` tag |
| `make release-major`, `release-minor`, `release-patch` | Release the next major, minor or patch version with RTK. Dates the `## [Unreleased]` CHANGELOG.md entries as the release, then commits and tags `aem-orchestrator-<version>` locally; push with `git push --follow-tags` |

### Release requirements
- A GPG key for signing, with its public key on a keyserver such as `keyserver.ubuntu.com`
  (Maven Central verifies signatures against it)
- A Maven Central Portal user token for the `com.shinesolutions` namespace
- Both are read from environment variables only, never from files. Enter them in your shell, so
  the values stay hidden and out of your shell history:

  ```
  # GPG private key: run this, paste the whole key including the
  # -----BEGIN/END PGP PRIVATE KEY BLOCK----- lines, press Enter, then Ctrl-D
  $ stty -echo; MAVEN_GPG_KEY="$(cat)"; stty echo; export MAVEN_GPG_KEY

  # GPG passphrase and Central Portal user token: type or paste each value, then press Enter
  $ read -rs MAVEN_GPG_PASSPHRASE; export MAVEN_GPG_PASSPHRASE
  $ read -rs MAVEN_CENTRAL_USERNAME; export MAVEN_CENTRAL_USERNAME
  $ read -rs MAVEN_CENTRAL_PASSWORD; export MAVEN_CENTRAL_PASSWORD
  ```

  Check the key arrived complete without printing it: `printf '%s\n' "$MAVEN_GPG_KEY" | head -1` and
  `| tail -1` should show the BEGIN and END lines.

Run the `make`, `mvn` and `git` commands below in aem-platform-buildenv, started from the directory
above this repository. It passes the variables through by name, your git identity for the release
commits, and marks the mounted repository as safe for git (it is owned by your user, not root):

```
$ docker run --rm -it -v "$(pwd)":/workspace -w /workspace/aem-orchestrator \
    -v ~/.gitconfig:/root/.gitconfig:ro \
    -e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory \
    -e GIT_CONFIG_VALUE_0=/workspace/aem-orchestrator \
    -e MAVEN_GPG_KEY -e MAVEN_GPG_PASSPHRASE -e MAVEN_CENTRAL_USERNAME -e MAVEN_CENTRAL_PASSWORD \
    shinesolutions/aem-platform-buildenv:6.3.0 bash
```

### Release steps
1. Start from an up-to-date `master` with a green CI build and a clean working tree. Check that the
   `## [Unreleased]` entries in CHANGELOG.md describe everything in this release.
2. Check signing and the Maven Central bundle without uploading anything:
   ```
   $ make release-check
   ```
3. Create the release, either:
   - In GitHub Actions, run the **Release Major**, **Release Minor** or **Release Patch** workflow.
     It runs RTK and pushes the commits and the tag. Then `git pull --tags` to fetch them.
   - Or locally, choosing `release-major`, `release-minor` or `release-patch`:
     ```
     $ make release-major
     ```
     This dates the `## [Unreleased]` entries as the new version in CHANGELOG.md, commits the release
     version, tags it `aem-orchestrator-<version>` and commits the next pre-release version. Nothing
     is pushed. Review the result with `git log -3` and `git show aem-orchestrator-<version>:CHANGELOG.md`.
4. If you released locally, push the commits and the tag from your machine, outside the container,
   where your GitHub credentials are:
   ```
   $ git push --follow-tags
   ```
5. Upload the tagged version to Maven Central. The pushed tag triggers the **Publish to Maven
   Central** workflow, which runs `make publish` in aem-platform-buildenv with the
   `SHINEOPENSOURCE_MAVEN_CENTRAL_USERNAME`, `SHINEOPENSOURCE_MAVEN_CENTRAL_PASSWORD`,
   `SHINEOPENSOURCE_MAVEN_GPG_KEY` and `SHINEOPENSOURCE_MAVEN_GPG_PASSPHRASE` GitHub secrets. To
   upload it yourself instead:
   ```
   $ git checkout aem-orchestrator-<version>
   $ make publish
   $ git checkout master
   ```
   Maven Central validates the upload (signatures, checksums, POM, sources and javadoc) and the build
   waits until it is validated. The deployment then waits at
   [central.sonatype.com](https://central.sonatype.com) → Publishing → Deployments: click **Publish**
   to release it, or **Drop** to discard it without publishing. A published version can't be changed
   or removed. To publish automatically once validated, run `make publish MVN="mvn -B -ntp -DautoPublish=true"`.

   Without a Central Portal login, use the user token and the deployment ID printed by `make publish`:
   ```
   $ make release-status DEPLOYMENT_ID=<id>
   $ make release-drop DEPLOYMENT_ID=<id>
   ```
6. Unset the secrets when you are done:
   `unset MAVEN_GPG_KEY MAVEN_GPG_PASSPHRASE MAVEN_CENTRAL_USERNAME MAVEN_CENTRAL_PASSWORD`
